# 桥健壮性方案：多进程 worker + 共享任务队列

> 拟定：2026-10-03（当晚实测取证） · 涉及仓库：CatClaw.Qemu（guest 工具链）+ CatClawVideo（宿主侧桥客户端）
> 状态：**待实施**（阶段 1 可直接开工；阶段 2 依赖阶段 1 的队列/回队机制）

## 一、问题

**ART 桥**是 guest 内的**单个**进程（`artlaunch bridge.GuestMain`），所有 jar 源共用它。
桥崩 = **原生 SIGSEGV**（`[sig] s=11 a=0 … /memfd:jit-cache`，JIT 代码内空指针），
`try/catch`、全局异常钩子、FirstChance 全部无效 —— 段错误是进程级的。

宿主当前的处理是**把整个 VM 杀掉重来**：

```
[jvm] 桥读循环退出
[jvm] 桥无响应（读循环退出（桥进程死亡））→ 重置爬虫引擎：丢掉当前桥会话，期间请求立刻报错
[jvm] 爬虫引擎已重置，下一次调用会重新起桥（ART guest 约 15s）
[qemu] 进程退出
```

**实测代价**：恢复要等一次完整 VM + 桥冷启动（~15~20s）；期间**所有**请求立即失败；
搜索（并发打几十个站）表现为「全灭 → 用户看到未找到」。

当晚证据链（Windows 端）：

| 时间 | 事件 |
|---|---|
| 20:31 / 20:41 | 解析 871KB / 453 集后桥 SIGSEGV（`s=11 a=0`，崩在 jit-cache）|
| 20:50:08 | 桥读循环退出 → 引擎重置 → QEMU 进程退出 |
| 21:19 | 用户搜索「择日飞升」：Windows 0 条；同源同词**手机 112 条**（Android 走进程内 DexSpiderRuntime，无 QEMU）|

WinDbg 崩溃桶（历史同类）：
`STOWED_EXCEPTION_80004005_CoreMessagingXP.dll!DispatcherQueue::DeferInvokeCallback`（那是另一条线，已修）。

## 二、目标 / 非目标

**目标**
1. **站点数不减少**：崩掉的站在恢复后**自动补搜**，最终结果集完整
2. **速度不降**：**不动 JIT**（`-Xint` 会让慢站超时 → 站点变少，已否决）
3. **恢复快**：从「~20s 全灭」降到「~2s、只丢在飞的少数站」
4. **阶段 1/2 都不碰 initrd**（只动宿主侧；发行载荷不变）

**非目标**
- 修复 ART/JIT 崩溃本身（那是 guest 侧另一条线：禁 JIT / 强制 mterp / 上游修）
- 提升单请求吞吐（网络与 jar 自身耗时占大头，见 §五 基线）

## 三、设计

```
        ┌──────────── 站点任务队列（一次搜索 = 全量站点入队）────────────┐
        │  每个 worker 同时在飞 ≤ 2 个站点                                │
        └───┬───────────┬───────────┬───────────┬───────────────────────┘
            ▼           ▼           ▼           ▼
        worker1     worker2     worker3     worker4      ← guest 内 4 个独立 ART 进程
        :18600      :18610      :18620      :18630        各有自己的 jar 缓存
            │           │           │           │
            └───────────┴─────┬─────┴───────────┘
                      worker 死亡 → 它在飞的 2 个站回队 → 幸存者接走
```

**关键规则**

1. **任务在共享队列**（不是预先分片）：worker 做完一个再拉下一个 ⇒ 负载天然均衡
2. **每 worker 在飞 ≤ 2**：单进程压强低 ⇒ 崩的频率本身下降（当晚正是并发把桥压崩的）
3. **worker 死亡 ⇒ 未完成任务回队**，最多重派 1 次（防死循环）；重派后仍失败才算永久失败
4. **死亡 worker 重启**：宿主经既有通道拉起新桥进程（优先 adb 隧道 18603；不可用时回退旧路径）
5. **汇总口径**：`最终结果 = 全量站点 - 永久失败站点`，并在状态栏如实显示「已完成 N/M 个站点」

## 四、阶段

### 阶段 1（N=1）：把队列/回队/重启/补搜做出来
- 搜索改为「任务队列 + 单 worker 拉取」，失败站点回队，桥重启后自动重跑
- 桥崩溃：**不再杀 VM**，只重启桥进程
- **验收**
  - 桥崩后 ≤ 3s 内恢复（日志出现新的「桥就绪」）
  - 崩一次只丢失当次在飞的站（≤2），其余站结果不受影响
  - 补搜后**最终站点数 = 全量**（除永久失败）
  - 无回归：正常搜索耗时与现状持平（±10%）

### 阶段 2（N=3~4）：多 worker
- guest 内并排起 N 个桥进程（宿主经 adb 拉起，各自端口）
- 宿主侧：连接池 + 每 worker 一个客户端 + 任务队列分派
- 宿主 QEMU 参数增加对应 hostfwd 端口（**宿主侧参数**，不动 initrd）
- **验收**
  - 单 worker 崩溃：其分片内站点失败 ≤ 在飞数，其余 worker 持续出结果
  - 搜索总耗时**下降**（总并发 4×2=8，高于现状单桥 3）
  - guest 内存占用在 6GB 内（见 §六）
  - 二次搜索命中各 worker 的 jar 缓存 ⇒ 明显快于首次

## 五、指标与基线（均为当晚实测）

| 指标 | 现状 | 阶段 1 目标 | 阶段 2 目标 |
|---|---|---|---|
| 桥冷启动 | ~15s | 不变（N=1）| ~15s（但只在必要时）|
| 桥崩恢复 | ~20s（杀 VM）| **≤3s** | **≤3s** |
| 崩时影响面 | **全部站点** | ≤2 个在飞站 | ≤该 worker 在飞站 |
| 结果完整性 | 崩后整轮丢失 | **补搜后完整** | 完整 |
| 搜索并发 | 3（单桥）| 3 | **8**（4 worker × 2）|
| `searchContent` 单站耗时 | Wogg 843ms / 长泽 483ms / zhiqiu 953ms / FishPs 3758ms | 持平 | 持平或更快 |
| guest 内存 | 4096MB → **6144MB（已提）** | 6144MB | 6144MB（N=4 时观察）|

## 六、风险与回退

| 风险 | 缓解 |
|---|---|
| guest 内存不够（N 个 ART 进程）| 已从 4GB 提到 **6GB**（`-m 6144` 实测生效 ✓）；不够继续加（宿主 31.9GB）|
| 依赖 adb 拉起桥 | 取不到 adb 时**回退旧路径**（杀 VM 重启），保证不变差 |
| 阶段 2 端口/hostfwd | 全部在宿主参数里加，**不动 initrd**；端口冲突走配置 |
| jar 缓存分散到各 worker | 首搜变慢（每 worker 各自加载）→ 用「按站点亲和」把常用站固定到同一 worker |
| 崩的频率本身没降 | 阶段 1 的补搜已保证结果完整；进一步靠 §二 的 guest 侧另一条线 |

**回退开关**：`N=1` + 旧「杀 VM 重启」路径保留为可选策略，一行配置切换。
