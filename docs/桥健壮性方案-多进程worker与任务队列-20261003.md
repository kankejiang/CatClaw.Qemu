# 桥健壮性方案：多进程 worker + 共享任务队列

> 拟定：2026-10-03（当晚实测取证） · 涉及仓库：CatClaw.Qemu（guest 工具链）+ CatClawVideo（宿主侧桥客户端）
> 状态：**待实施**（阶段 1 可直接开工；阶段 2 依赖阶段 1 的队列/回队机制）

## 一、问题

**ART 桥**是 guest 内的**单个**进程（`artlaunch bridge.GuestMain`），所有 jar 源共用它。
桥崩 = **原生 SIGSEGV**（`[sig] s=11 a=0 … /memfd:jit-cache`，JIT 代码内空指针），
`try/catch`、全局异常钩子、FirstChance 全部无效 —— 段错误是进程级的。

宿主当前的处理是**把整个 VM 杀掉重来**：

```
[jvm] 桥读循环退出
[jvm] 桥无响应（读循环退出（桥进程死亡））→ 重置爬虫引擎：丢掉当前桥会话，期间请求立刻报错
[jvm] 爬虫引擎已重置，下一次调用会重新起桥（ART guest 约 15s）
[qemu] 进程退出
```

**实测代价**：恢复要等一次完整 VM + 桥冷启动（~15~20s）；期间**所有**请求立即失败；
搜索（并发打几十个站）表现为「全灭 → 用户看到未找到」。

当晚证据链（Windows 端）：

| 时间 | 事件 |
|---|---|
| 20:31 / 20:41 | 解析 871KB / 453 集后桥 SIGSEGV（`s=11 a=0`，崩在 jit-cache）|
| 20:50:08 | 桥读循环退出 → 引擎重置 → QEMU 进程退出 |
| 21:19 | 用户搜索「择日飞升」：Windows 0 条；同源同词**手机 112 条**（Android 走进程内 DexSpiderRuntime，无 QEMU）|

WinDbg 崩溃桶（历史同类）：
`STOWED_EXCEPTION_80004005_CoreMessagingXP.dll!DispatcherQueue::DeferInvokeCallback`（那是另一条线，已修）。

## 二、目标 / 非目标

**目标**
1. **站点数不减少**：崩掉的站在恢复后**自动补搜**，最终结果集完整
2. **速度不降**：**不动 JIT**（`-Xint` 会让慢站超时 → 站点变少，已否决）
3. **恢复快**：从「~20s 全灭」降到「~2s、只丢在飞的少数站」
4. **阶段 1/2 都不碰 initrd**（只动宿主侧；发行载荷不变）

**非目标**
- 修复 ART/JIT 崩溃本身（那是 guest 侧另一条线：禁 JIT / 强制 mterp / 上游修）
- 提升单请求吞吐（网络与 jar 自身耗时占大头，见 §五 基线）

## 三、设计

```
        ┌──────────── 站点任务队列（一次搜索 = 全量站点入队）────────────┐
        │  每个 worker 同时在飞 ≤ 2 个站点                                │
        └───┬───────────┬───────────┬───────────┬───────────────────────┘
            ▼           ▼           ▼           ▼
        worker1     worker2     worker3     worker4      ← guest 内 4 个独立 ART 进程
        :18600      :18610      :18620      :18630        各有自己的 jar 缓存
            │           │           │           │
            └───────────┴─────┬─────┴───────────┘
                      worker 死亡 → 它在飞的 2 个站回队 → 幸存者接走
```

**关键规则**

1. **任务在共享队列**（不是预先分片）：worker 做完一个再拉下一个 ⇒ 负载天然均衡
2. **每 worker 在飞 ≤ 2**：单进程压强低 ⇒ 崩的频率本身下降（当晚正是并发把桥压崩的）
3. **worker 死亡 ⇒ 未完成任务回队**，最多重派 1 次（防死循环）；重派后仍失败才算永久失败
4. **死亡 worker 重启**：宿主经既有通道拉起新桥进程（优先 adb 隧道 18603；不可用时回退旧路径）
5. **汇总口径**：`最终结果 = 全量站点 - 永久失败站点`，并在状态栏如实显示「已完成 N/M 个站点」

## 四、阶段

### 阶段 1（N=1）：把队列/回队/重启/补搜做出来
- 搜索改为「任务队列 + 单 worker 拉取」，失败站点回队，桥重启后自动重跑
- 桥崩溃：**不再杀 VM**，只重启桥进程
- **验收**
  - 桥崩后 ≤ 3s 内恢复（日志出现新的「桥就绪」）
  - 崩一次只丢失当次在飞的站（≤2），其余站结果不受影响
  - 补搜后**最终站点数 = 全量**（除永久失败）
  - 无回归：正常搜索耗时与现状持平（±10%）

### 阶段 2（N=3~4）：多 worker
- guest 内并排起 N 个桥进程（宿主经 adb 拉起，各自端口）
- 宿主侧：连接池 + 每 worker 一个客户端 + 任务队列分派
- 宿主 QEMU 参数增加对应 hostfwd 端口（**宿主侧参数**，不动 initrd）
- **验收**
  - 单 worker 崩溃：其分片内站点失败 ≤ 在飞数，其余 worker 持续出结果
  - 搜索总耗时**下降**（总并发 4×2=8，高于现状单桥 3）
  - guest 内存占用在 6GB 内（见 §六）
  - 二次搜索命中各 worker 的 jar 缓存 ⇒ 明显快于首次

## 六、风险与回退

| 风险 | 缓解 |
|---|---|
| guest 内存不够（N 个 ART 进程）| 已从 4GB 提到 **6GB**（`-m 6144` 实测生效 ✓）；不够继续加（宿主 31.9GB）|

## 八、阶段 1 补漏（2026-10-10 实测取证）

> 本节记录「桥崩连带杀 VM」的根因与修复，供后续排查比对。

### 8.1 崩溃本身的性质（已取实锤）

ART 日志里 9 次崩溃**每一次的 PC 都落在 `/memfd:jit-cache (deleted)`**（PC 区间 `0x43xxxxxx`–`0x45xxxxxx`）：

| 行号 | 信号 | PC | 崩溃点 |
|---|---|---|---|
| L41348 | s=11 | 43e4d17f | `43e35000-45e35000 r-xs … /memfd:jit-cache (deleted)` |
| L84792 | s=11 | 43fff9e4 | `43fca000-45fca000 r-xs … /memfd:jit-cache (deleted)` |
| L86424 | s=11 | 4396d10e | `43958000-45958000 r-xs … /memfd:jit-cache (deleted)` |
| L87030 | s=11 | 4381bfe4 | `43805000-45805000 r-xs … /memfd:jit-cache (deleted)` |

即 ARM 代码经 ndk_translation 软转译后，**执行刚编译出的 JIT 代码时段错误**。
紧邻崩溃前的现场几乎都是超大响应：`[srv] Wogg.detailContent 耗时 4952ms，结果 886780 字节`。

> ⚠ `init_x86.sh:82` 记录的「Round57：-Xint 验证还崩（PC 同为 fb17）→ 凶手不是 JIT，已回滚」
> 说明**关 JIT 不能规避**（性能代价 3-5 倍且仍崩）。按 §二 的非目标，
> 崩溃本身留给 guest 侧另一条线；本节只做「崩了不牵连 VM + 响应不丢」。

### 8.2 「桥崩连带杀 VM」的真正根因（阶段 1 漏做的一半）

2026-10-04 的改动已让 `FailAllPending` 不再 `Shutdown()`，注释写着「VM 与 guest 里的 /init 监督器都要留着」，
**但同一方法仍把 `_art` 摘成 null**：

```csharp
Interlocked.Exchange(ref _art, null);   // ← 这一行让承诺落空
```

而 `EnsureBridgeAsync` 里是 `lock (_artCreateLock) { _art ??= CreateArtGuest(); }` ——
只看字段是否为空。于是 `ScheduleBridgeRecoverFallback` 的 5s 轮询**第一轮就新建实例 = 起新 VM**。

实测时间线（`home-debug.log`，修复前）：

```
15:11:41.885 [jvm] 桥读循环退出
15:11:58.238 [qemu] 进程退出                    ← VM 被杀（本不该发生）
15:11:58.246 [qemu] 已启动 pid=41088 媒体口=18606  ← 端口从 18601 跳到 18606
15:12:10.803 [jvm] ART guest 里的桥就绪          ← 16.3s 恢复（目标 ≤3s）
```

guest 的 /init 监督器本来能在 ~2s 内原地重启桥（日志 `[init] 2s 后重启桥(18600)`），
是这个 `_art = null` 把 2s 又变回 16s。

### 8.3 修复

`FailAllPending` 改为**只摘 socket 流、保留 `_art` 实例**。
`ConnectAsync` 见 `_vm.IsRunning == true` 时 `StartVmLockedAsync` 直接返回，
探针循环只去连 guest 内已重生的桥 —— VM 与 /data（网盘登录态）全程不动。
`_art` 只在真正换 VM 的 `ResetBridge → Shutdown()` 路径才清。

副链收益：`_art?.PersistentDataDisk` / `_art?.ProxyBase` 在不换 VM 时继续命中同一实例，
隧道端口不用重新探测。

### 8.4 附带修掉：迟到响应被丢弃（数据源加载为空的直接原因）

旧实现超时即 `TryRemove` 丢弃 waiter，桥侧 `lane.submit` 异步发出的响应抵达时已无主 →
走进「未匹配响应」分支被静默丢弃。现场两种丢法：

| 丢法 | 现场 | 后果 |
|---|---|---|
| 超时丢弃 | `id=595` 在 48.902s 抵达，与 25s 超时差 1 毫秒被丢（内容 `{"list":[]}`）| 首页空数据源 |
| 调用方取消丢弃 | `init` 只花 **2ms** 的站（`spider AppGet init 完成 (2ms)`）也刷「未匹配响应 id=39」| 白跑的 load 全丢 |

两条路径都改为把 waiter 转交 `_lateResponses`，由迟到响应或宽限到期回收。
宽限窗口**按实测最慢桥端耗时自适应**（下限 45s，上限 180s）：

- 固定 45s 仍会漏 —— Libvio 站宿主 10s 超时而桥侧实耗 **65.9s**（`spider Libvio init 完成 (65890ms)`），迟到 58s > 45s；
- 记录每次应答的端到端耗时，慢站会把窗口抬到够用的宽度。

握手类短 op（`ping`/`setProxyPort`/`exit`/`probe`/`netstat`）不参与迟到窗口：它们超时应立刻按「桥有问题」处理。
桥死时一次性作废全部迟到 waiter（旧桥响应永不会来，且 id 会复用）。

### 8.5 撤回两个被实测否证的「根因」（重要，别再走一遍）

本节记录两条**曾经写进代码、后来被实验推翻**的假设，以及推翻它们的实测证据。
留着是为了防止下一个人（或下一轮的我）再花同样的时间。

#### 8.5.1 「fishso 白名单修复已生效」是空集，不是修复

当时的结论：「修 linker 白名单后 `/thunder/data/fishso/` 失败从 2000 次降到 0」。
实际是**分母为 0**：同一个 boot 里 `FishCrypto SO load failed` 记 0 次，但
`FishCrypto` 这个词**一次都没出现过** —— Guard 壳的 `DexNative.<clinit>` 在更早一步
（`/thunder/data/cache/.ftyfn*` 的 `System.load`）就抛 `UnsatisfiedLinkError` 并中止了
整个站的 init，后面的 FishCrypto 步骤**根本没机会执行**。

教训：验证「某步骤失败次数下降」之前，必须同时确认**该步骤确实被走到了**
（同 boot 内的前置阶段完成标记）。按 boot 分段统计、别跨运行取窗口，才能发现这类空集。

#### 8.5.2 `System.load` 失败与**路径无关**（已实验否证）

假设：ndk_translation 判定「路径受支持」只看路径是否含 `/lib/arm`
（`libndk_translation.so` 里 grep 到的唯一路径判定常量，对应官方 app
`/data/app/<pkg>/lib/arm64` 的目录约定），因此把 `nativeLibraryDir` 与
`DexClassLoader` 的 `librarySearchPath` 从 `.../art/lib` 改成 `.../art/lib/arm64`。

**探针实验（已部署并跑过，结论如下）**：把**同一份**已知可被桥加载的 arm64 ELF
（`/system/lib64/arm64/libc++.so`，671496B）复制到 6 个路径逐一 `System.load`：

| 候选路径 | 结果 |
|---|---|
| `/data/catclaw/art/cache/probe.so` | `UnsatisfiedLinkError: EM_AARCH64 (183)` |
| `/data/catclaw/art/lib/arm64/probe.so`（含 `/lib/arm`） | 同上，失败 |
| `/data/catclaw/art/lib/probe.so` | 同上，失败 |
| `/data/catclaw/art/opt/probe.so` | 同上，失败 |
| `/data/catclaw/art/files/lib/arm64/probe.so`（含 `/lib/arm`） | 同上，失败 |
| `/system/lib64/arm64/probe_copy.so`（**原目录同目录**） | 同上，失败 |

6/6 全灭，含「含 `/lib/arm`」和「原路径同目录」这两个最该过的样本 ⇒ **路径无关**。
两处改动已回滚，代码里留了注释防止改回去。

#### 8.5.3 真正的分水岭是**调用者**，不是路径

同一次 boot 内 artlaunch 自己的审计日志给出互斥的两行 —— 同一个
`/system/lib64/arm64`，一次成功一次判否：

```
NativeBridgeLoadLibrary(arm64 libc++.so) = OK          ← artlaunch 直调回调，成功
NativeBridgeIsPathSupported(/system/lib64/arm64) = 0    ← 同一目录，判定为不支持
System.load(/system/lib64/arm64/probe_copy.so) → 失败
```

⇒ 桥**有**加载 arm64 的能力（ndk 转译层正常），缺的是 ART 侧把 classloader 的
`namespace` 标记为 bridged 的那条通路。`System.load` 的委派判据是 **namespace**
级别（不是路径级别）；artlaunch 直调 `NativeBridgeLoadLibrary` 绕过了它，所以成功。

**下一步该查的地方**：

1. ~~`libnativebridge.so` 的 `GetExportedNamespace`/`CreateNamespace`~~ —— 见 8.6，
   这条路（把真实现替换进 `/system/lib64`）已被实测否证；
2. artlaunch 的 `LoadNativeBridge` 传进去的 9 个 runtime callbacks 是否**缺一**
   （`g_runtime_callbacks` 少某个指针时 ndk 侧会静默降级）—— **仍未验证**；
3. ~~`NativeBridgeIsAvailable` 从未被打印~~ —— 原因已查明：那个符号名根本不存在，
   libnativebridge.so 导出的是 `NativeBridgeAvailable`（没有 `Is`）。

注：`libnativebridge.so` 不在 `/system/lib64`（那里只有 5488B 的
`libnativebridge_lazy.so`，仅 4 个符号）；真正的转发 stub 在 APEX 里。

> 旧审计块（artlaunch.c L469-493）整体无效，**两个独立缺陷**：
> 1) 跑在 `InitializeNativeBridge` **之前**，ndk 尚未 initialize，所有判定都是假值；
> 2) 用了不存在的符号名 `NativeBridgeIsAvailable`，`dlsym` 返回 NULL ⇒ 整段
>    `if (isAv)` 永不执行 —— 这就是「从未被打印」的真实原因，不是「桥不可用」的证据。
>
> 已在 `InitializeNativeBridge` 之后新加审计块（artlaunch.c 的「审计 3」）修正这两点。

### 8.6 第三个否证：nativeloader 拿到的**不是** `_lazy` 桩（已回滚）

根据符号表推断的假设：`/system/lib64` 只有 `libnativebridge_lazy.so`（5488B，导出 6 个
符号：`Needs/PreInitialize/Available/Initialized/GetTrampoline/Error`），而
`libnativeloader.so` 要的是另外 7 个（`IsPathSupported/CreateNamespace/LoadLibraryExt/
LinkNamespaces/GetExportedNamespace/InitAnonymousNamespace/UnloadLibrary`），两组完全不重叠
⇒ nativeloader 全部符号解析落空 ⇒ namespace 永不 bridged。

**验证方式**：把 APEX 里的真 `libnativebridge.so`（15168B，含全部转发实现与
`LoadNativeBridge`/`InitializeNativeBridge`）复制到 `/system/lib64/libnativebridge.so`，
重打 initrd 部署。

**结果：假设不成立。** 本次 boot 实测 `EM_AARCH64` 仍 **125 次**，与替换前同量级。
⇒ nativeloader 并不通过 `/system/lib64` 这个路径解析 libnativebridge（它走 APEX 的
linker namespace，本来就能拿到完整实现）。该替换已回滚。

这条路的教训：**符号表长得像缺东西，不等于 ART 真的加载了它。** 链接器 namespace
决定解析顺序，静态看文件布局推不出运行时绑定关系 —— 必须用 `dladdr` 打印实际加载路径
才能确认（而 `dladdr` 需要重编 artlaunch，见 8.7）。

### 8.7 工具链：artlaunch 可以在 WSL 里重编（bionic 头不在，但可绕）

`/root/x86guest` 构建机已关，但 artlaunch 重编**不必依赖它**：

- 目标 ABI 是 x86_64 + musl 风格动态链接，`apt install musl-tools` 即可；
- 缺 `jni.h` → 从宿主 JDK（`C:\Program Files\Android\openjdk\jdk-21.0.8\include`）拷；
- 缺 `jni_md.h`（宿主 JDK 只有 win32 版）→ 自写一份 LP64 类型集（jint/jlong/jbyte 等）；
- `__system_property_get` 是 bionic 私有符号（运行时由 `LD_PRELOAD` 的 proppreload.so 提供）
  → 源码里加 `__attribute__((weak))` 弱声明即可编过，解析不到也不崩；
- `AttachCurrentThread(&e3)` 在 JDK 21 的 jni.h 下类型不严格 → 显式转 `void**`；
- 编译命令：`musl-gcc -O2 -D_GNU_SOURCE -I jniinc -I jniinc/linux -o artlaunch.new artlaunch.c -ldl`。

⚠ **未验证的风险**：新二进制链的是 Debian glibc 的 `libc.so`，而 guest 里是 **bionic**。
`dlopen` 的 namespace 语义两者不同（bionic 支持 per-namespace 库搜索路径），换 libc 可能
让 artlaunch 在 guest 里 dlopen 行为改变甚至加载失败。部署后必须先看 artlaunch 是否还能
正常启动（日志锚点：`artlaunch: libart ready, JNI_CreateJavaVM=...`）。
长期正解是给 WSL 装 bionic 工具链或恢复 `/root/x86guest`，不要长期依赖 glibc 产物。

⚠⚠ **实测结果（2026-10-10 23:46）：上述 musl-gcc 产物部署后，guest 里 artlaunch 起不来**
—— 本次 boot `libart ready` = 0、`JNI_CreateJavaVM` = 0，桥从未就绪。
glibc↔bionic 的 ABI 不兼容是**实锤**，这条路当前不可用，改动已全部回滚。

上述步骤仍有价值：它揪出了 `AttachCurrentThread` 的类型问题和 `__system_property_get`
的隐式依赖。但要真正部署，必须给 WSL 装 bionic 工具链，或恢复 `/root/x86guest`。

**当前卡点**：唯一能改 artlaunch 运行时行为的入口就是重编它，而重编被工具链卡住。
本轮新增的「审计 3」因此暂时拿不到运行时数据 —— `dladdr` 究竟打印哪个 so、
nativeloader 需要的 7 个符号解析率多少，现在**仍是未知数**（不是「已验证没问题」）。

## 九、✅ 根因定位与修复（2026-10-11 00:00）

### 9.1 根因

**classloader 的 `nativeLibraryDir` 必须是 `/data/app/<pkg>/lib/arm64` 这个形状，
ndk_translation 的 `NativeBridgeIsPathSupported` 才返回 1。**

证据来自 artlaunch 重编后新增的运行时审计（在 `InitializeNativeBridge` **之后**问，
时序正确），本 boot 三次重复完全一致：

```
/data/catclaw/art/lib       = 0
/data/catclaw/art/cache     = 0
/thunder/data/cache         = 0
/system/lib64/arm64         = 0
/data/app/com.x/lib/arm64   = 1   ← 唯一为 1
```

旧值 `/data/catclaw/art/lib` → 判为 not-bridged → 壳的 arm64 so 落到宿主 bionic
`dlopen` → `is for EM_AARCH64 (183) instead of EM_X86_64 (62)`。

**§8.5 的探针为什么全灭**：那 6 条候选路径**没有一条带 `/data/app/` 前缀**，
所以 6/6 全灭是必然的，不是「与路径无关」。当时的推论方向错了 —— 不是路径无关，
是**没有一条候选路径踩中 ndk 的形状约定**。

### 9.2 修复

```java
// JavaBridge/src/bridge/Art.java
private static File nativeLibDir() {
    File pkg = new File("/data/app/catclaw.guest");
    File f = new File(pkg, "lib/arm64");
    f.mkdirs();
    return f;
}
// 两处消费：
ai.nativeLibraryDir = nativeLibDir().getAbsolutePath();
new DexClassLoader(jarPath, cache, nativeLibDir().getAbsolutePath(), sys);
```

### 9.3 工具链（关键突破，可长期复用）

**artlaunch 可以在宿主用 Android NDK 重编，不需要 `/root/x86guest` 那台构建机。**

```powershell
$cc = "$env:LOCALAPPDATA\Android\Sdk\ndk\27.0.12077973" +
      "\toolchains\llvm\prebuilt\windows-x86_64\bin\x86_64-linux-android28-clang.cmd"
cmd /c "$cc -O2 -Wl,--export-dynamic -o artlaunch.nb artlaunch.c -ldl"
```

产物链 **bionic**（`NEEDED: libdl.so, libc.so`，与原版一致），可直接进 initrd。

⚠ 两个坑：
- **不要用 WSL 的 musl-gcc**（§8.7）：链 glibc，部署后 artlaunch 起不来，
  本次 boot `libart ready`=0。NDK 才是对的工具链。
- `rebuild_gb.cmd` 会用 pristine 的 23344B artlaunch 覆盖 NDK 产物 ——
  每次重建后必须**重新注入**（`art_initrd_x64.gz` → 解包 → 替换 → 打包）。

顺带修掉的两个真实问题：`AttachCurrentThread` 的参数类型（应为 `JNIEnv**`）、
`__system_property_get` 缺显式声明（bionic 私有符号，运行时由 proppreload.so 提供，
已加 `__attribute__((weak))`）。
